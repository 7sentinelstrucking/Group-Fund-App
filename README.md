# Group Fund App

A single-fund group fundraising web app. One shareable link, one admin, card
payments through PayPal, and a public record everyone can see: running total,
progress bar, per-contributor progress, a monthly scoreboard, and a full
payment ledger.

**Money flow:** contributor card → PayPal → the admin's PayPal account → the
admin's bank. The app never holds money. Nothing is recorded in the ledger
unless the payment is confirmed (PayPal webhook, signature-verified).

## Quick start (local)

```bash
cd ~/workspace/fund-app
npm install
cp .env.example .env   # then edit .env (at least SESSION_SECRET)
npm start
```

Open http://localhost:3000. The app runs in **demo mode** until PayPal
credentials are configured — a "Demo pay" button simulates a confirmed payment
so every flow can be clicked through with no real money moving.

## The roles

- **Admin (one seat).** The app starts with the admin seat open. The first
  person to register as admin claims it permanently — a second claim is
  refused (409). After that, the registration page only offers contributor
  signup. The admin then configures the fund: name, goal amount, number of
  contributors, monthly amount per contributor, monthly due day, and their
  PayPal API credentials.
- **Contributors.** Register via the shared link (name, email, phone,
  password), pick/upload an avatar (changeable anytime), and pay by
  credit/debit card through PayPal Checkout — no PayPal account needed.

## What everyone sees

- Fund goal, running total of confirmed payments, animated progress bar.
- Per-contributor progress: their share (goal ÷ contributors) vs. the **true**
  total they have paid (never capped — overpayments show in full).
- Green dot on a contributor's avatar once they reach their full share.
- Monthly scoreboard: green = paid on time (by the due day), yellow = paid
  late, blank = missed.
- Full ledger: every confirmed payment with avatar, name, true amount, date.

## Going live with real payments

1. The admin creates a **PayPal Business** account at paypal.com.
2. At developer.paypal.com, they create an app and copy the **Client ID**
   and **Secret**. For live money, the app must use live credentials
   (`PAYPAL_MODE=live`).
3. In the PayPal developer dashboard, add a webhook subscription for
   `PAYPAL.CAPTURE.COMPLETED` pointing at
   `https://YOUR-DOMAIN/api/webhooks/paypal`, and copy the **Webhook ID**
   into `PAYPAL_WEBHOOK_ID`. Webhook events without a valid signature are
   rejected — the app fails closed.
4. Deploy the app somewhere with public HTTPS (PayPal webhooks require it):
   Render, Railway, Fly.io, or any Node host. Set the env vars from
   `.env.example` there, especially `SESSION_SECRET` (long random string).

## Admin email notifications

On every confirmed payment the app emails the admin (contributor name,
amount, new total). Configure SMTP in the env (`SMTP_HOST`, `SMTP_PORT`,
`SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`). If SMTP is not configured,
notifications are logged to the console and stored in the DB (visible on the
admin dashboard) — the app never crashes for lack of mail config.

## Environment variables

See `.env.example` — every setting is documented there. Admin-entered PayPal
credentials (in the setup screen) take precedence over the env fallback.

## Data

SQLite file at `./data/fund.db` (override with `DB_PATH`) — the local-dev
default. Avatar uploads are stored **in the database** (BYTEA/BLOB + mime
type), never on disk, so the app is safe on hosts with ephemeral disks.

## Production (Render + Neon Postgres)

1. Create a free Postgres database at [neon.tech](https://neon.tech) and copy
   its connection string.
2. Deploy this repo on Render via the included `render.yaml` Blueprint
   (free web service; build `npm install`, start `npm start`, health check
   `/api/status`).
3. In the Render dashboard, set `DATABASE_URL` to the Neon connection string.
   `SESSION_SECRET` is auto-generated by the Blueprint.
4. On first boot the app creates all tables itself — no migrations to run.

When `DATABASE_URL` is set, **everything** lives in Postgres: fund data,
users, payments, avatars, and sessions. SQLite remains the local default when
`DATABASE_URL` is unset — no code changes needed to switch.
